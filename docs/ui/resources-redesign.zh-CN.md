## 0. 一句话

把现在「**一排不知道是什么的按钮 + 一张只有字段名的表**」，改成「**一张能一眼扫完的网关能力地图**」：
每个资源先回答**它是干什么的、配了会怎样、不配会怎样、配错了会怎样**，再让你进去配置。

其中「**配错了会怎样**」是本次设计最重要的新增概念——因为网关对配置错误的反应有三种，
后果差得很远，而其中一种（**静默不生效**）在今天的界面上完全看不见。

## 1. 你提的问题，落到代码上是三个具体缺陷

| 你的原话 | 代码上的证据 | 用户的实际遭遇 |
|---|---|---|
| 「界面上有一堆东西」 | `web/src/views/Resources.vue:669-678`：15 个平铺按钮，`flex-wrap`，无分组、无说明、无条目数 | 不知道该点哪个；也无法一眼看出「这 15 个里我用了几个」 |
| 「不知道它是干什么的」 | 全页唯一的解释是 `web/src/i18n/locales/zh-CN.js:302` 的一句 `resources.hint`，而这句话**只提到 5 种资源**（MCP 服务器、A2A 智能体、OIDC 提供方、可观测性导出器、Claim 映射），页面上却有 **15 种** | 按这句话去找「团队 / 预算 / 计费价目」的解释，一个都找不到——**页面上的说明本身就是错的** |
| 「不知道配置以后会是什么效果」 | ① 列表列头是字段名（`mcp_servers` 的列是 `name/type/url/auth_type/enabled`，`Resources.vue:608`），未映射的列名**原样输出英文**（`colLabel` 兜底 `return c`，`Resources.vue:643`）；② 表单标签是英文 snake_case 原字段名（`auth_type`、`forward_client_headers`、`leeway_secs`、`resolve.api_key`，`Resources.vue:723-1132`）；③ 全流程没有任何「配了之后哪条路径会通、返回什么状态码、指标里会出现什么」 | 用户只能靠猜。而最坏的情况不是猜错，是**猜对了也没生效，且界面不告诉他** |

### 1.1 还有两处更结构性的事实

**（一）15 种里有 7 种，控制台明确表示「不帮你」**

`Resources.vue:43-51` 的 `RAW_YAML_ONLY`（teams / users / pricing / budgets / budget_policy /
usage_accounting / mcp_policies）= 7 种，弹窗里只显示一句
「该资源类型结构较复杂，请用「原始 YAML」标签页编辑」（`zh-CN.js:324`）。
用户被明确告知：这 7 件事，本控制台不提供服务，请自己去写 YAML。

**（二）网关拒绝了你的配置，但你在保存它的那个页面上看不到**

控制台保存后会调网关重载，而网关对**行级**失败的处理是：丢掉这一行、其余照常加载、
把原因记进 `GET /status/config` 的 `rejected[]`，状态变 `degraded`
（上游 `crates/aisix-etcd/src/loader.rs:601-712`）。

控制台确实拿到了这份数据（`server/src/gateway.js:31-34` 拉 `/status/config`，
`server/src/routes/status.js:12-36` 原样透出），也**确实显示了**——但**只在「总览」页**
（`web/src/views/Dashboard.vue:113-127`）。

于是形成一条最坏的体验链：**在「资源集成」里点保存 → 提示「已保存」→ 网关丢了这一行 →
没有任何效果 → 用户不知道去哪看原因。** 这正是你说的「不知道配置以后会是什么效果」最尖锐的形式。

**（三）顺手发现的一处真实缺陷（可直接改）**

`Dashboard.vue:117` 与 `:133`，两张表的**第一列是资源类型**，表头却写成
`t('app.nav.providerKeys')` = 「上游密钥」。也就是说「被拒绝的资源」那张表，
第一列的表头是「上游密钥」。同一个 bug 复制到了两张表。这正是你说的
「界面上有一堆东西，但我不知道它是干什么的」的一个样本。

## 3. 设计目标与三条原则

**一句话目标**：让用户不查文档、不问人，就能知道「网关支持哪些事、我现在用了哪些、每件事该不该配、配完怎么确认它生效了」。

**原则一：先讲用途，再讲字段。**
现在恰恰相反。任何资源出现在任何位置，都先给固定的六问答案（见 §5.2），字段永远排在后半段。

**原则二：按人的心智分组，不按数据模型的顺序。**
现在的按钮顺序是集合名的罗列顺序。用户心里想的是「我要把模型接进来」「谁在花钱」，
所以按**请求的生命周期**分四组：接入 → 授权与身份 → 治理 → 计量与观测。

**原则三：效果必须落到可核实的判据。**
不写「已生效」，写「发出后应当观察到：响应头带 `x-aisix-cache: hit`」
「`/status/config` 的计数从 23 变 24」。凡是没有判据的说明，就等于没有说明。

## 4. 新信息架构

### 4.1 一级页面：资源目录

四组、21 种资源。每种一张卡片。

| 组 | 组说明（写在组标题下） | 资源 |
|---|---|---|
| **接入** | 把模型和外部服务接进网关。这一组是地基：没有它，后面的授权和治理都没有对象。 | 上游密钥、模型、MCP 服务器、A2A 智能体、透传路由 |
| **授权与身份** | 决定每一个请求算谁发的、能用哪些东西。网关据此鉴权、限流、记账。 | 调用方密钥、团队、成员、OIDC 提供方、Claim 映射、MCP 认证设置、MCP 访问策略 |
| **治理** | 请求放行之后在网关里怎么被处理：拦什么、缓存什么、限多少。 | 护栏、护栏附件、缓存策略、限流策略 |
| **计量与观测** | 花了多少钱、用量发去哪。这一组不决定请求能否通过，但决定你能不能算清账。 | 计费价目、预算、预算策略、用量记账、可观测性导出器 |

**为什么是 21 种而不是现在的 15 种**：`server/src/resources.js:16-39` 的 `KINDS` 就是
21 种，`resources.yaml` 里它们平级。控制台把其中 6 种放到了别的页面
（上游密钥、模型、调用方密钥各有专属页；护栏、缓存策略、限流策略在「策略」页），
**但没有任何地方告诉用户这件事**。

所以「资源集成」的新定位是：**整份 `resources.yaml` 的地图**。已有专属页面的资源，
卡片不提供编辑，而是写明「在「模型」页维护」并给跳转——**一处编辑，一处地图，不产生第二个编辑入口。**

这样做顺带修掉一个真实的管理断层：现在「护栏」在「策略」页、「护栏附件」在「资源集成」页，
而附件离开护栏完全无法理解（它就是一个指向护栏的外键 + 一个作用范围）。
分组之后两者在**同一组内相邻**，用户能看懂「先建规则，再挂上去」。

### 4.2 二级页面：资源详情

从卡片进入。结构见 §5.2。

### 4.3 对比表

| | 现在 | 重新设计后 |
|---|---|---|
| 入口 | 15 个无说明的按钮 | 4 组 × 21 张卡片，每张一句话定位 + 当前条目数 + 最大的坑 |
| 说明 | 1 句通用文案，且只覆盖 5/15 | 每资源 6 问，文案随资源切换 |
| 列表 | 列 = 字段名（部分英文） | 列 = 人关心的问题，全中文 |
| 表单 | 英文字段名，无说明 | 中文字段名 + 原字段名 + 一行说明 + 必填标记 + 常见坑提示 |
| 失败反馈 | 保存后只提示「已保存」；网关拒绝的行只在「总览」可见 | 资源目录顶部有网关反馈条；被拒行列出资源类型 / ID / 网关给的原因 |
| 「不配会怎样」 | 从未说明 | 每个资源明确写 |
| 「配错会怎样」 | 从未说明 | 每个资源按三种失败模式分别写 |
| 7 种无表单资源 | 一句「请用原始 YAML」 | 明确标注「只有原始 YAML」，并把它列为待补清单 |

## 5. 页面规格

### 5.1 资源目录页

自上而下：

1. **页头**：标题「资源集成」；右侧一行汇总「21 种资源 · 已配置 N 种 / 共 M 条 · 原始 YAML 入口」。
2. **网关反馈条**（§5.4）。
3. **首次配置引导**：「第一次配置，按这个顺序走通一条链路：① 上游密钥 → ② 模型 → ③ 调用方密钥 → ④ 可观测性导出器」，
   末尾一句「走通之后，再回来配「治理」和「计量」」。
   四个步骤可点击直接跳到对应资源。
4. **失败模式图例**（默认折叠）：一行标题「配错了会怎样？网关有三种反应，后果差很多 —— 展开看区别」。
5. **四个分组**，每组：组名 + 「N 种 · 已配 M」+ 组说明 + 卡片网格（`auto-fill, minmax(320px, 1fr)`）。

**卡片规格**：

```
┌────────────────────────────────────────────┐
│ 上游密钥                          6 条     │  ← 名称 + 条目数（未配置 = 灰「未配置」）
│ 把某个上游厂商的 API Key 存一次，让多个模型共用…│  ← 一句话定位
│                                            │
│ 作用  引用它的模型能正常调用；GET /admin/v1/… │  ← 配了会怎样
│ 不配  引用它的模型每个请求都返回 400          │  ← 不配会怎样
│ 坑    provider 不是 openai 又没填 api_base → │  ← 本资源最贵的错（琥珀色）
│       每个请求 400，不是 502                 │
│ ────────────────────────────────────────── │
│ 在「上游密钥」页维护             前往 →      │  ← 归属页 + 动作
└────────────────────────────────────────────┘
```

「坑」这一行是**每种资源只写它自己最贵的那一个错**。不写「本资源可能静默失效」——
每张卡都写等于没写。全部 21 条「坑」见 `catalog.js` 的 `traps`。

### 5.2 资源详情页

页头：面包屑（资源集成 / 组名 / 资源名）+ 资源名 + 条目数 + `[+ 新增]`。

**核心是这块说明带**，六问固定顺序、固定标签，用户扫一眼就知道去哪找答案：

| 标签 | 内容 | 为什么需要它 |
|---|---|---|
| **它是什么** | 一句话，外行能懂 | 回答「这是干什么的」 |
| **什么时候要** | 场景 + 不配的替代方案 | 回答「我现在需要配吗」 |
| **配了会怎样** | 可观察的效果：状态码、响应头、指标名、管理接口 | 回答「配了有什么用」 |
| **不配会怎样** | 明确写出默认行为 | 回答「不配行不行」 |
| **和谁有关** | 引用字段 + 目标是哪个集合 + **按 id 还是按名字** | 用户最容易错在引用关系上 |
| **配错会怎样** | 按三种失败模式分别列，每条前面带徽章 | 回答「为什么我配了没效果」——见 §7 |
| **怎么验证** | 一条命令或一个判据 | 回答「我怎么知道它生效了」 |

下面再接列表（列名全中文）与新增/编辑。

### 5.3 表单（弹窗 / 抽屉）

- **标签中文化**，右侧小字保留原字段名（便于和 `resources.yaml` 对照）。
- **每个字段一行说明**，说明写「填什么、为什么、填错的后果」，不写「请输入名称」这类废话。
  - 例：`name` → 「两处身份：URL 里的 `/mcp/<名>`，以及工具命名空间前缀 `<名>__<工具>`。不能含 `__`，不能以 `_` 结尾。」
  - 例：`credential_ref` → 「这里填的是一个**名字**，不是密钥本身。网关启动时从它自己的环境变量里按这个名字取密钥——只填名字而环境变量没配，导出会静默失败。」
- **必填标记**只在 schema 真正 required 的字段上（现在的表单凭感觉标 `*`）。
- 抽屉顶部给一条「最常见的坑」，下面给一份可展开的「填错了会怎样（N 种）」。
- 保存按钮的文案保留「保存并重载网关」——它诚实说明了保存会触发重载，这一点现在做对了。

### 5.4 网关反馈条（本次最关键的交互补丁）

**状态正常时**（绿色、一行）：

```
[网关 synced]  文件 36 条 · 本次加载全部通过 · 无被拒行        最后重载 09:41
```

**有被拒行时**（红色，列出每一行）：

                                         /routing: missing property "targets"
guardrail_attachments   b71d0e55-…       semantic validation failed: priority is required

数据侧**不需要新接口**：`server/src/routes/status.js:12-36` 已经把整个 `/status/config`

## 6. 内容规格：21 个资源要写什么

全部文案在 `docs/ui/mockup/catalog.js`（唯一来源，视觉稿直接读它渲染），
实施时搬进 `web/src/i18n/locales/{zh-CN,en}.js`，
键名 `resources.kind.<key>.{oneLiner,whenNeeded,effect,ifAbsent,verify,misconfig.*}`。

摘要（「坑」= 卡片上那一行；失败模式见 §7）：

| 资源 | 它是什么 | 不配会怎样 | 坑 |
|---|---|---|---|
| 上游密钥 | 上游厂商的 API Key 存一次，多模型共用 | 引用它的模型每个请求 400 | provider 非 openai 又不给 api_base → 400，不是 502 |
| 模型 | 对外开放的模型名与它落到的上游模型 | 404 `model_not_found` | provider_key_id 填错 → schema 能过，请求时 400 |
| MCP 服务器 | 注册工具来源，工具以 `<名>__<工具>` 暴露 | `/mcp/<名>` 404 | auth_type 要密钥却漏填 → 加载时整行被拒 |
| A2A 智能体 | 把外部智能体挂到 `/a2a/<名>` | 404 | `enabled: false` 也是 404，不是 403 |
| 透传路由 | 按路径/域名把非模型流量直通上游 | 落到 fallback，404 | provider_key_id 不存在 → 每个请求稳定 400 |
| 调用方密钥 | 调用方凭据，库里只存 SHA-256 | 所有请求 401 | 三个授权字段都不填 → 能认证但所有模型 403 |
| 团队 | 团队名与成本归属标签；**不参与认证和路由** | 指标 `team_name=unknown` | 文档 id 必须等于 key 的 team_id |
| 成员 | 成员名与成本归属标签；同样不参与认证路由 | `user_name` 回落到 key 自身字段 | 没填 user_id 的 key 不受 team_member 约束 |
| OIDC 提供方 | 信任外部签发的 JWT | JWT 被当密钥查哈希 → 401 | name 与 `api_keys.jwt_provider` 拼写不一致 → 永远 401 |
| Claim 映射 | 按 claim 条件把一类身份映射到一把密钥 | 只能一对一填 jwt_subject | priority 是**越小越先**（与护栏附件相反） |
| MCP 认证设置 | 每环境一份：OAuth 发现面 + 匿名入口 | 一切照旧，无发现面 | 写了第二条 → 两项设置一起休眠 |
| MCP 访问策略 | 环境/团队级工具访问控制 | **不是全开而是全关** | `allow: []` 等于禁止全部 |
| 护栏 | 内容检查规则本身 | 不检查任何内容 | 有规则、没附件 = 不检查任何流量 |
| 护栏附件 | 把护栏挂到模型/密钥/团队等 | 护栏等于摆设 | priority 漏填整行被拒；**数字最大者胜** |
| 缓存策略 | 复用上次的回答 | 每个请求都打上游 | `applies_to` 拼错 → 静默放大到整个环境 |
| 限流策略 | 按对象或条件树设上限 | 没有这一层限制 | 两种形式混用整行被拒；没有每小时/每秒令牌字段 |
| 计费价目 | 每 1000 token 的价钱 | 回落到模型内联 cost | `pricing_key` 少一个字符 → 静默回落 |
| 预算 | 硬停的花费上限 | 没有预算拦截 | **文件模式下预算不生效** |
| 预算策略 | 用量送不到控制面时怎么办 | 默认 sticky，不额外拒绝 | closed + 投递坏掉 → 大面积 503，别只找 429 |
| 用量记账 | 估算 token 算不算进令牌限流 | 一视同仁都占额度 | 只影响令牌窗口，请求数照旧计数 |
| 可观测性导出器 | 把遥测直接从数据面发到外部后端 | 数据只留在网关本地 | credential_ref 只是名字，环境变量没配 → 静默失败 |

### 6.1 文案的依据与边界（重要）

## 7. 三个失败模式（本次设计最重要的新增概念）

网关对配置错误的反应有三种，**后果差得很远**，而今天的界面对这三者一视同仁（都是「已保存」）：

| 模式 | 触发条件 | 后果 | 用户看到什么 |
|---|---|---|---|
| 🔴 **整份文件被拒**（通道级） | 缺 `id`、`id` 不是小写带连字符 UUID、同一集合 `id` 重复、`_format_version` 不是 `"2"`、`${VAR}` 未设、YAML 解析错 | 启动时**网关起不来**；SIGHUP 重载时**保留旧配置继续服务**，状态 `out_of_sync` | 网关没起来 / 配置改了没生效但服务还在 |
| 🟠 **仅这一行被丢弃**（行级） | schema 校验不过、语义校验不过、反序列化不过 | 其余行照常加载，状态 `degraded`，`rejected[]` 有记录 | 只有这一个资源没生效，别的一切正常 |
| ⚪ **静默不生效** | 配置**合法**、加载**成功**，但从不命中（引用指向不存在的对象、作用域语义错位、字段被忽略、默认值反直觉） | 没有任何报错、没有任何指标变化 | **什么都没有发生。** |

依据：`crates/aisix-etcd/src/file_source/mod.rs:16-34`（通道级）、
`crates/aisix-etcd/src/loader.rs:639-662, 698-710`（行级）。

**为什么把它单独拎出来**：你现在最痛的「不知道配置以后会是什么效果」，
最尖锐的形式就是第三种——用户做对了每一步操作，界面也回了「已保存」，
但网关永远不会用上这条配置，而且**没有任何地方会告诉他**。
所以设计上做了三件事：

1. 每个资源在详情页按三种模式分别列出它的具体陷阱（§5.2）；
2. 目录页给一次性的图例（§5.1 第 4 项）；
3. **把静态可判定的静默失效变成运行期提示**——见 §7.1。

### 7.1 已实现：生效自检

控制台手上**已经有整份 `resources.yaml`**，所以下列静默失效全都可以在本地算出来，
不需要网关配合、不需要网关侧新接口。它把「静默不生效」从一句文档说明，变成界面上的一条警告。

实现：`server/src/effectChecks.js`（纯函数，14 条）+ `GET /api/resources/effect-checks`。
**检查项返回的是 code 与参数，不是句子**——控制台是双语的，且测试该断言行为而不是措辞；
文案在 `resourceCatalog.check.*`（中英各 14 条）。

| # | code | 判定 | 为什么它值得提示 |
|---|---|---|---|
| 1 | `guardrailNoAttachment` | `enabled` 的护栏没有被任何附件引用 | 规则不检查任何流量——最常见的「配了没用」 |
| 2 | `attachmentDanglingGuardrail` | 附件的 `guardrail_id` 不在 `guardrails[].id` 里 | 网关静默跳过，只打一条 warn |
| 3 | `attachmentNoPriority` | 附件缺 `priority` | 必填无默认值，整行会被丢弃 |
| 4 | `providerKeyNoApiBase` | 无 `api_base` 且 provider 不是 openai（或空 provider + adapter openai） | 只有 openai 有内置默认地址，其余请求 400 |
| 5 | `budgetInFileMode` | `budgets` 非空 | 文件模式下预算不执行：耗尽标记由控制面写 |
| 6 | `mcpDefaultDeny` | 有 MCP 服务器，但无环境策略、无团队策略、无密钥授权 | MCP 访问默认「全关」，直觉相反 |
| 7 | `mcpPolicyEmptyAllow` | 策略的 `allow`（或 `allow_ids`）是空数组 | 等于禁止该层全部访问，不是「不限制」 |
| 8 | `cacheAppliesToUnknown` | `applies_to` 非空且不匹配 `all` / `model:` / `api_key:` | 网关当成「全部」，作用域被静默放大 |
| 9 | `rateLimitMixedForms` | 同时出现经典字段与条件字段 | 整行被拒，不是部分生效 |
| 10 | `rateLimitUnknownField` | 出现 `tph` / `tps` 等不存在的字段 | 没有每小时/每秒令牌限制，字段被忽略 |
| 11 | `teamNoKey` | 团队 `id` 不被任何 `api_keys[].team_id` 引用 | 指标无名、团队级限流与预算匹配不到请求 |
| 12 | `memberNoKey` | 成员 `id` 不被任何 `api_keys[].user_id` 引用 | 同上，作用域是成员 |
| 13 | `claimMappingProviderMissing` | `jwt_provider` 不在 `oidc_providers[].name` 里 | 该映射永不被评估，token 一律 401 |
| 14 | `pricingUnused` | 价目 `key` 不被任何 `models[].pricing_key` 引用 | 死配置；反向错误（模型无价）更难发现 |

呈现方式：反馈条里的「生效自检」区块，**默认折叠、有命中才展开**，带一句「以下不是错误，
而是『配置合法但不会生效』的提示」。不做成阻断——它是提示，不是校验器。

两条测试护栏，防止这份清单和文案将来各自漂移：
- `server/test/effectChecks.test.js`（23 条）断言每个 code 都可达、没有未声明的 code 被发出、
  **健康配置不产生任何命中**（会误报的提示比没有提示更糟），以及每条发出的参数与 `CHECK_PARAMS` 契约一致；
- `web/test/resourceCatalog.test.js` 断言文案与 `CHECK_CODES` **双向**一致，
  且每条文案用到的占位符与 `CHECK_PARAMS` 完全相同——否则用户会看到字面量 `{n}`。
