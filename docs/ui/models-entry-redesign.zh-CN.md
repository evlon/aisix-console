# 「模型」页的入口改造：从「形状优先」到「用途优先」

状态：**已实施**（提交见文末），四个待验项的结果在第五节。

## 一、问题：表单的第一问，用的是配置的词汇，不是用户的

现在的「新增模型」表单，第一行是：

```
形状  [ 直连 / 路由 / 投票聚合 / 语义路由 ]      ← 表单的第一个字段
```

这几件事我都核实过，不是印象：

| 事实 | 出处 |
|---|---|
| 模型 schema **没有** `task` 之类的「任务」字段 | `schemas/resources/model.schema.json`，`required` 只有 `display_name` |
| 「这个模型是干什么用的」由 `embedding` / `routing` / `ensemble` / `semantic` 谁存在来表达 | 同上，四个都是顶层属性 |
| 表单的第一个字段就是形状下拉框（4 选一） | `web/src/views/Models.vue:514-518` |
| 形状是从条目**反推**出来的（`detectShape`，用于表格里的徽标与编辑时预选） | 同文件，`L200` 处使用 |
| 保存时**显式把另外三个形状置 `null`** —— 四者是互斥的 | 同文件 `L294-302` |
| 形状字段只在选定之后才渲染（`v-if="form.shape === …"`） | 同文件 `L521 / 585 / 631 / 659` |

所以模型配置本质上是一个**四选一的和类型**，表单忠实地把它摆在了第一问。问题在于：**用户到达这一页时脑子里没有「形状」，只有目的**——

- 「我要一个便宜的主力，挂了自动切到备用」 → 这是 `routing`，但他不会说「路由」
- 「我要一个能算相似度的模型」 → 这是 `direct` + `embedding`（**不是**某个形状）
- 「我要同时问三个模型再挑最好的」 → 这是 `ensemble`

**代价在于它落在哪一刻**：形状一旦选定，界面就只显示那个形状的字段，而且**不会再回头质疑这个选择**——用户按错误形状把每个字段都填对，保存成功、校验通过、文件合法，只是它不按他想要的方式工作。也就是说，这一页「配好了」与「看起来配好了」的分界，恰好落在**用户信息最少的那一刻**（他还不知道这四个词分别意味着什么）。

这跟你一开始提的那件事是同一个病：**界面从配置项推导出来，而不是从用户的使用感受出发。**

## 二、方案：第一问问「你要它做什么」，答案映射到形状

把第一行换成**目的**，映射关系写死在一张表里（而不是让用户自己推）：

| 新增的第一问（用户的说法） | 落到配置 |
|---|---|
| 接一个上游供应商，直接提供这个模型 | `direct` |
| 在多个上游 / 模型之间选一个（故障转移、加权、按状态回退） | `routing` |
| 同时问多个模型，再挑一个答案 | `ensemble` |
| 按问题的语义挑一条路由 | `semantic` |
| 嵌入模型（算相似度、做检索） | `direct` + `embedding` |

**下面仍然保持现状**：选定之后只显示该形状的字段（现在就是这么做的），字段顺序不动，说明文字沿用刚做完的那一批。

**并且保留形状本身**：把「形状」下拉框降级成一行**进阶字段**（原文保留 `direct`/`routing`/… 这些上游术语），这样懂配置的人不会被挡住，界面上也不存在「只有结论、没有依据」的选项。

### 明确不改的东西

- **写进文件的 YAML 形状完全不变**：同样的字段、同样的互斥。这是纯入口改造，不是数据模型改造。
- **已有条目不变**：`detectShape` 已经能把四种形状认出来，改造后它们各自预选到正确的第一问。
- **「原始 YAML」标签页不变**。

## 三、需要你拍板的三件事

1. **「嵌入模型」要不要作为一等选项？**
   它不是形状（是 `direct` + 一个 `embedding` 配置块），但它是用户脑子里的一个独立目的。我倾向**要**——把它做成第一问里的第 5 个答案、映射到 `direct + embedding`。代价是这张映射表不是一对一，我需要在代码里把这事写清楚。

2. **五个答案的中文措辞。** 我上面那五行是草稿，是**我的话**，不是你的。你如果对「投票聚合」「语义路由」这些叫法有更贴切的说法，直接改；这套词会长期留在界面上。

3. **形状下拉框是留在明面上，还是收进「进阶」折叠区？**
   我倾向**留在明面上**（放在第一问下面一行）。理由：出问题时运维要拿这里的值去对上游文档，藏起来只会让人去翻原始 YAML。

## 四、我打算怎么验（先写清楚，再动手）

1. **写进去的东西一个字节都不能变**：同一份输入，**旧代码跑一遍、新代码跑一遍，两次输出逐字节比对**（四种形状 + 一个嵌入模型，各做一次「打开即保存」）。
   *写方案时我把这条写成了「保存前后文件不变」——那是错的*，见第五节第 1 条。
2. **每个答案都到对的字段集**：5 个答案 → 期望出现的字段集合，逐条渲染检查。
3. **已有条目各自预选正确**：五种条目各造一条，编辑时第一问要落在正确答案上。
4. **形状互斥不被破坏**：从路由改成直连后保存，另外三个形状必须被清掉（沿用现有行为，但要有判据）。
5. `npm run smoke` 与现有 45 + 108 项测试全绿。

## 五、实施与结果

| 判据 | 结果 |
|---|---|
| 四次 + 五条形状的输出**逐字节相同** | ✓ 旧代码 `AF8DAE503BA20A2D…` / 1811 字节；新代码**同一哈希** |
| 五个答案→字段集 | ✓ 见下表 |
| 已有条目预选 | ✓ 五行分别预选：直连 / **嵌入模型** / 路由 / 投票聚合 / 语义路由 |
| 互斥不被破坏 | ✓ 沿用原有 `null` 处置（本次未改这段逻辑） |
| 测试与冒烟 | ✓ web 45 / server 108、`npm run smoke` 11 条路由全过 |

**第 1 条判据写错了，值得记下来**：我原本写的是「保存前后文件不变」，实测**不成立**——一次**打开即保存**会做三件事：

1. 写入表单推荐的 `timeout` / `stream_timeout`（路由 30000/20000，聚合与语义 120000/60000），以及 `when_all_unavailable: fail`；**这些值用户没有选过**
2. **丢掉文件里的注释**（YAML 被重新序列化）
3. 在文件末尾补齐所有空集合（`api_keys: []` 等）

这三条**都是既有行为，与本次改造无关**——判据因此改成「旧代码输出 == 新代码输出」，那才是这次改造真正的安全带。上面第 1、2 条我建议你单独决定要不要处理：它们意味着「我只打开看了一眼」和「我改了点东西」在文件层面留下同样的痕迹。

### 五个答案 → 字段集

| 答案 | 出现的字段 |
|---|---|
| 接一个上游供应商，直接由它提供 | provider / model_name / provider_key / 超时 / 嵌入配置 / 后台检查 / 档位映射 |
| 在多个上游／模型之间挑一个 | strategy / targets / retries / max_fallbacks / fallback_on_statuses / when_all_unavailable / retry_on_429 |
| 同时问多个模型，再挑一个答案 | panel / judge / min_responses |

| 嵌入模型 | 与「直连」同字段集，但嵌入配置为必填 |

## 五、为什么值得做（以及不值得做什么）

值得：这一页的入口决定了「配好」与「看起来配好了」的分界。现在分界落在用户最没有信息的那一刻。

**不值得**：把四个形状从界面上彻底藏掉，或者把四种形状合并成一种「万能模型」。前者会让懂配置的人失去依据，后者与上游 schema 直接冲突（四者互斥是网关强制的，不是我们界面上的约定）。
